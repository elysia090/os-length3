## Derivation: keep residual phase, not elapsed periods

Binary modes 0 and 2 (raw mode 6 alias included) are admitted on all three
channels. The normative mode-2 behavior is the manufacturer's
[Intel 8254 datasheet](https://www.scs.stanford.edu/23wi-cs212/pintos/specs/8254.pdf),
pages 9 and 12: OUT starts high, is low for the CE=1 pulse, reloads N at the
cycle boundary, and a newly written CR waits for that boundary. Gate low
forces OUT high; its rising edge loads the latest CR on the next pulse.
Zero denotes 65,536; divisor 1 is illegal. BCD, other modes, command reads
and wide I/O remain explicit refusals, not constant successful device reads.

```text
t(ns) = (ns / 10^9) * 1193182 + ((ns % 10^9) * 1193182) / 10^9
phase p in [0,N), current count = N - p
d = t(new) - t(anchor)
r = N - p
if d < r:  p' = p + d
otherwise: crossed = true; activate pending CR; p' = (d - r) mod N'
OUT = high except p' = N' - 1 (with gate/load overrides)
```

The first loading pulse does not decrement. An initial load or gate restart
consumes that pulse before applying the formula. Incomplete low/high writes
keep an existing mode-2 CE running. Mode-0 incomplete writes instead stop it.
Independent unread count/status latches and raw mode bits remain observable.
These distinctions are state, not a history of pulses or sampled snapshots.

Advancement is O(1) per channel regardless of crossed periods. IRQ0 drives the
common PIC: its edge IRR coalesces intervening rising edges, while final OUT
preserves level-triggered mode. An unchanged level is not re-driven after PIC
reset; an identical accepted clock timestamp adds no edge. All channels are
prevalidated before mutation. Common C clock acceptance advances PIT/PIC,
RTC and UART; JavaScript provides only the already declared clock event.

Redundant `paused` and `null_count` copies are absent: the write phase and
`!loaded || pending` derive them. The owner remains **128 bytes**, three
40-byte channels, as before mode 2. No period queue or payload allocation.
Asynchronous timer deadline / HLT wake independent of guest I/O/RDTSC is
still missing; this receipt does not establish full periodic Linux timing.

## POST is a device, not an opcode skip

The virtual board owns a 2-byte `{byte, valid}` write-only POST latch at port
0x80. Only privileged/admitted 8-bit OUT commits its exact byte, in order,
through the ordinary C I/O path. IN, wider I/O, other unknown ports, stale
machine state and competing event frontiers still refuse. Close/rebind clears
the latch. A supervisor-only `vm_post_read(generation)` observes it; it is not
an import available to emitted guest functions. It is 0 in this actual run.

Linux's original `arch/x86/kernel/io_delay.c` uses port 0x80 by default;
the [kernel parameter documentation](https://www.kernel.org/doc/html/v6.11/admin-guide/kernel-parameters.html)
also documents that selection. Ordered completion is consistent with the
[Linux port-I/O contract](https://www.kernel.org/doc/html/latest/driver-api/device-io.html).
This virtual latch does not claim real ISA bus delay. Neither kernel bytes nor
command line are changed to bypass the access; guest time is not fabricated.
