# Privileged halt / activity boundary — 2026-10-06

## Shared meaning and red

The completed normal `a305af4` Linux diagnostic refused HLT `f4` at
`0xffffffff813efa53`, after the guest had already failed its s6 transition.
This does not make HLT the cause of the earlier service failure.
The frozen old compiler is also red in the expanded interrupt-provider check:
its first HLT emission returns -102 instead of zero.

[Intel SDM, HLT](https://cdrdv2-public.intel.com/812383/253666-sdm-vol-2a.pdf)
(Vol. 2A, HLT, PDF page 598) specifies a privileged halt with unchanged flags,
CPL violation #GP(0), LOCK #UD, and interrupt continuation after the instruction.
RF clearing at successful retirement is the existing common cut rule.

The common x86 frontend validates a no-operand, precise privileged halt and
retains its fallthrough. Native formation and cold Wasm lowering use that
same predicate. Generated code applies the existing CPL0 fault check, then
the ordinary success epilogue publishes RIP, RF and one retirement before
returning HALT/0. No opcode callback, source decoder or new guest import.

The C dispatcher accepts HALT only for a one-instruction row with exact
fallthrough, consumes the old STI/MOV SS shadow, counts its committed prefix
once, and stops. A separate four-byte machine activity owner survives source
eviction and directory close/rebind. Pending boundaries return HALT without
fetch/select/call. Only successfully accepted interrupt/exception delivery,
or a cold machine reset, changes it to running. IF=0 does not invent a wake.
The supervisor-only `vm_halted` getter is not an emitted guest import.

Exact suspend must retain this activity along with CPU/device state. Merely
adding the word/getter does NOT prove complete suspend serialization/recovery.
NMI/SMI/reset/debug wake projections are not implemented by this IRQ check.
