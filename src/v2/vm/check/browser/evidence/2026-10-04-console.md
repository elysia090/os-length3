## One minimal external-byte frontier

Derive the required distinctions from future observations:

```text
request -> accepted -> consumed
same (generation, port, RIP, ticket, byte) while requested = same wait
same acknowledgement while accepted/consumed = duplicate, no new output
changed tuple / cancelled binding / exhausted sequence = reject
UART device commit and source retirement occur only after acceptance
```

The common C owner stores 48 bytes: issued high-water, current ticket,
generation, RIP, private port, exact byte and stage. There is no output queue,
payload allocation, full-state snapshot, guest opcode or tty/syscall model.
The latest consumed tuple answers an exact duplicate. A new byte replaces
that tuple; older replies are rejected rather than retained in an unbounded
history. Closing preserves the non-wrapping issue high-water. Rebind cancels
the frontier. A fresh Worker must receive a fresh broker generation.

Generated IN/OUT retain the same scalar `machine.io` ABI. C performs the
context/TSS/privilege checks and publishes the new CONSOLE barrier (26),
ticket, one-byte extent, request class and exact value. Only the supervisor
receives `vm_console_commit`: 1 means first acceptance, 0 an exact duplicate,
-1 rejection without mutation. The sink reserves capacity **before** accepting
and publishes a byte only on 1. The diagnostic has a fixed 16,384-byte local
observation sink; reaching capacity returns an explicit gate without accepting
or dropping the next byte. Text rendering is an observation, not a terminal
or arbitrary-binary encoding contract.

The one-instruction table continuation remains pinned through the wait.
UART TX effects, RIP/RF, retirement and old STI/MOV-SS inhibition are unchanged
until the accepted retry succeeds. A changed borrowed row, source contents or
fetch permission cannot substitute a different continuation. Competing device
and clock operations cannot consume the ticket. Ordinary RMW abort cannot
undo output admission; explicit close/rebind fences subsequent replies.

This is local transport acceptance, **not** durable external output or an
exactly-once crash-recovery protocol. Already published bytes cannot be undone.
Reconnecting an external sink or restoring an exact suspended machine requires
a matching broker replay/dedup policy. No such recovery acceptance is claimed.

## Largest fixed cost: placement is not executable identity

The [pre-reuse console run](2026-10-04-console-slot-browser.json) reached the
same refusal and emitted the same 4,532-byte console observation, but rebuilt
1,823,976 engines with zero hits. Its reuse key was the C source owner's
rotating placement slot. Slot replacement usually associates unrelated code
with that key, so it discards a still reusable executable candidate.

The candidate key is now the C-admitted source coordinate, independently of
placement. This key is **not** a semantic equivalence proof: every miss still
runs the C compiler, and `CompiledModules` requires exact newly emitted bytes
to reuse an instance with the same Worker-owned imports. Changed body/limit,
invalid emission, close/reopen and independent memory owners retain their
guards. A table-slot relocation and changed-body negative witness are tested.
Reuse is restricted by the trusted C compiler's stateless cut-module output
ABI. The helper is not an arbitrary-Wasm validator and this is not a reusable
module/start/global-state contract.

The candidate pool allows at most 1,024 entries and **the same 262,144-byte
emitted-witness cap**. The actual run retains 760 entries / 261,806 bytes.
The C source owner still has 64 rows / 6,752 metadata bytes / zero copied
source payload, and the table still has 64 live slots. Browser engine code,
per-instance overhead, separately pinned table functions and JS metadata are
not measured RSS and must not be called a 256 KiB total-memory bound.
